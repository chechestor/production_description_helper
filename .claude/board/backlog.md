#### Задача
`POST /api/generate` принимает тело с JSON товара и проверяет его до вызова LLM. Сначала проверяется сессия (F003): без входа ответ 401 `unauthorized`, даже если JSON битый. Потом — JSON.

Ошибки возвращаются единым телом `{"error":{"code","message","details"}}`, `message` — на русском:

| Вход | Ответ |
|---|---|
| Тело не JSON | 400 `invalid_json`, в `message` — строка и столбец ошибки |
| JSON не объект | 422 `invalid_input` |
| `name` нет, пусто или только пробелы | 422 `missing_name` |
| Неверный тип: `name`/`manufacturer`/`description` не строка, `specs` не объект, значение `specs` не строка и не число | 422 `invalid_field`, в `details` — имя поля |
| `description` > 20 000 символов или в `specs` > 100 пунктов | 422 `too_large` |

Нормализация:
- числа в `specs` приводятся к строке;
- пробелы по краям обрезаются;
- значение `specs`, равное `null` или пустой строке, считается отсутствующим.

Недостающие данные не мешают генерации. Ответ содержит `missing_fields` — список строк на русском:
- отсутствующие или пустые `manufacturer`, `specs`, `description`;
- пустые значения `specs` в виде `specs.<ключ>`;
- базовые характеристики, которые не найдены во входе (определяет F005).

Лишние поля верхнего уровня игнорируются, ответ получает предупреждение `warnings: ["Поле <x> не используется"]`.

**Тестовые входы (pytest с параметром)**

Файлы аналитика `.claude/team/analyst/scratch/input/{tm-210,megeon-51020,incomplete-pd100}.json` копируются без правок в `examples/input/` в этой задаче (раньше — в F010). Тест прогона входов через проверку параметризован опцией pytest `--inputs`:
- `local` — по умолчанию: берёт все `*.json` из папки `--inputs-dir`, по умолчанию `examples/input/`. Ожидание: проверка проходит без ошибок.
- `feed`: скачивает YML-фид по `--feed-url` (по умолчанию ссылка из `.task/task.md`) и берёт офферы `--offer-ids` (по умолчанию `170353,189862`). Из каждого строит вход: `name` = `<name>`, `manufacturer` = `<vendor>`, `specs` = `{}`, `description` = `""`: других данных в фиде нет. Ожидание: проверка проходит, `missing_fields` содержит `specs` и `description`. Нет сети или оффера → тест пропускается (skip) с причиной, а не падает.
- XML разбирается стандартной библиотекой (`urllib`, `xml.etree`), без новых зависимостей.

### F005. Генерация карточки через OpenAI в графе LangGraph: промпт и формат ответа
- Статус: готова к разработке
- Родитель: F004
- Приоритет: P1
- Источник:
  - ТЗ п.3.2–3.4;
  - ТЗ п.4 (пять блоков результата);
  - ТЗ п.5 «Модель не должна выдумывать характеристики. Все технические значения должны браться только из входных данных. Если характеристика отсутствует, в результате должно быть указано: „данных нет“»;
  - ТЗ п.8 «Важно: не выдумывайте характеристики прибора»;
  - Owner: выход — JSON из API и Markdown («По умолчанию, начинай»);
  - Owner, 2026-11-04: «LLM должна быть OpenAI»; «…на Fast API с применением LangChain, LangGraph и передачей логов в Phoenix».
#### Задача
Генерация — граф LangGraph, который вызывается из `POST /api/generate` после проверки F004. Узлы:
1. `generate` — вызов OpenAI через LangChain (`ChatOpenAI` + `with_structured_output` по схеме `card`);
2. `check` — проверки F007;
3. переход `check → generate` не больше одного раза (повтор F007), иначе `check → assemble`;
4. `assemble` — сборка `missing_fields`, `warnings`, `markdown` кодом.

Состояние графа: вход, `card`, список нарушений, счётчик попыток. Каждый узел виден отдельным шагом в Phoenix (F006). Ответ `POST /api/generate` (200):
```text
{
  "card": {
    "seo_title": str,                          // ≤ 70 символов с пробелами
    "seo_description": str,                    // 800–1200 символов с пробелами
    "key_specs": [{"name": str, "value": str, "verified": bool}],
    "search_queries": [str],                   // 3–5 штук
    "commercial": {"audience": [str], "tasks": [str]}   // по 2–4 пункта
  },
  "missing_fields": [str],
  "warnings": [str],
  "markdown": str                              // собирается кодом из card, не моделью
}
```
Правила для промпта. Промпт хранится отдельным файлом или константой, чтобы README мог на него сослаться.
1. Технические значения — числа, единицы, диапазоны, классы, резьба, интерфейсы, питание — берутся только из `specs` и `description`, дословно.
2. `key_specs`:
   - все пункты `specs`;
   - характеристики, явно названные в `description`;
   - базовые характеристики из ТЗ п.2 — диапазон измерений, класс точности/погрешность, питание, тип корпуса, интерфейсы. Если такой нет во входе, она попадает с `value: "данных нет"`.
3. Если во входе два разных значения одного параметра (например, резьба «М12х1,5, G1/4» в `specs` и только M12×1,5 в `description`), модель не выбирает одно: в `value` идут оба значения как в источнике, в `warnings` — пометка «противоречие в данных: <параметр>».
4. `seo_title`: тип прибора + модель + производитель (если есть), без выдуманных свойств.
5. `seo_description`: для контент-менеджера B2B, без превосходных степеней, которых нет во входе, без цены, гарантий и сроков поставки, если их нет во входе. Если данных мало, текст короче по фактам, но пометок «данных нет» внутри текста не содержит.
6. `search_queries`: из названия, типа, производителя и значений входа, без несуществующих модификаций.
7. `commercial`: кому подходит и какие задачи решает. Только то, что следует из назначения и области применения во входе. Если их нет — общие формулировки по типу прибора без технических чисел.

`markdown` собирается кодом в разделы: «SEO-заголовок», «SEO-описание», «Ключевые характеристики» (таблица), «Поисковые запросы», «Для менеджера», «Недостающие данные», «Предупреждения».

### F007. Проверка ответа модели кодом и один повтор
- Статус: готова к разработке

После ответа модели код проверяет `card`:

- b) `seo_description` от 800 до 1200 символов;
- c) `search_queries` — 3–5 непустых строк;

### F008. Обработка ошибок LLM API
- Статус: готова к разработке
- Родитель: F005
- Приоритет: P1
- Источник: ТЗ п.5 «Код должен корректно обрабатывать ошибки API…»; ТЗ п.7 «Обработка неполных или некорректных данных»; Owner, 2026-11-04: «LLM должна быть OpenAI».
#### Задача
Ошибки OpenAI (исключения `openai.*`, которые пробрасывает LangChain) превращаются в понятный ответ с тем же телом `{"error":{"code","message","details"}}` (как в F004):

| Ситуация | HTTP | `code` | `message` (смысл) |
|---|---|---|---|
| Нет `OPENAI_API_KEY` | 503 | `llm_not_configured` | «Не задан ключ API, см. README» |
| Провайдер вернул 401/403 | 502 | `llm_auth_error` | «Ключ API отклонён» |
| 429 / перегрузка | 503 | `llm_rate_limited` | «Лимит запросов, повторите позже» |
| Нет ответа дольше `LLM_TIMEOUT` | 504 | `llm_timeout` | «Модель не ответила за N с» |
| Сеть, 5xx провайдера, прочее | 502 | `llm_unavailable` | «Сервис LLM недоступен» |
| Ответ не по схеме после повтора (F007) | 502 | `llm_bad_response` | «Модель вернула некорректный ответ» |

Ошибка пишется в лог контейнера одной строкой: код, тип исключения. Ключ, промпт и вход в лог контейнера не попадают. Промпты и ответы видны только в Phoenix (F006). Там же трасса запроса помечается ошибкой.

Если Phoenix недоступен, генерация работает как обычно: ошибка отправки трасс не превращается в ошибку API.

- [ ] На каждую строку таблицы — тест с моком исключения SDK.

- [ ] Запрос, упавший с ошибкой LLM, виден в Phoenix (F006) со статусом ошибки.
